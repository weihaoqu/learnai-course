Week 10: Complete Static Project and Deployment
Slide 1
60-minute deployment studio

Make your app complete and shareable.

Week 8 defined the app. Week 9 added one working interaction. Week 10 makes the static app file-ready, deployable, testable, and safe to share.

In class

Turn a local prototype into a complete static web project with a deployment checklist.

Outcome

A public static link, or a local-file fallback plus a deployment readiness packet.

Boundary

Static prototype only. No backend, login, secrets, API keys, private data, or advice-domain expansion.

Pacing: 4 minutes. Define "deployed" carefully: a public static prototype, not a secure service or authoritative advisor.
4-10 min

The Week 10 path has six checkpoints.

Deployment should happen as a checkpoint, not as a rushed final click.

Architecture

Know what files exist and what each does.

File-ready

Make the app readable, complete, and self-contained.

Local test

Run normal and edge cases before sharing.

Deploy

Publish static files or complete fallback.

Post-test

Open the link and test again.

Packet

Submit evidence, privacy note, and review note.

Completion is not complexity

Do not add five new features. Make the existing idea usable: states, labels, reset, optional storage, smoke tests, and deployment evidence.

10-18 min

Static app architecture is small on purpose.

A complete static project can be a single HTML file, or a small folder of public files. Every file that ships can be read by the browser.

Single-file path

index.html contains HTML, CSS, and JavaScript. Best for simple student prototypes.

Folder path

index.html, styles.css, app.js, and public assets. Best when the app is getting larger.

What deploys

HTML, CSS, JS, images, and sample data that are safe to be public.

What does not deploy

Secrets, private prompts, account tokens, real student data, hidden answer keys, or files with personal details.

Ask students to point to where structure, style, behavior, and data live in their own project.
18-28 min

Check whether the project is ready to deploy.

Click only the statements that are true for the current app. The goal is to find gaps before the app is public.

36-45 min

Deployment means making public files available at a link.

For this course, deployment means static hosting. If account setup blocks deployment, students use the fallback path and still learn the checklist.

45-52 min

Run the smoke test twice: before and after deployment.

A deployed app is not finished until the public link works and the boundary still holds.

52-56 min

Ask the agent for a complete-project polish pass.

The prompt should ask for completion and deployment readiness, not new features.

Final artifact

Week 10 Complete Project Packet

Submit evidence that the app is complete enough to share as a static prototype.

After class

Homework: deploy or complete the fallback packet.

Students should leave Week 10 with a shareable static prototype or a concrete deployment-ready local artifact.

Required

Submit the Week 10 Complete Project Packet, a link or local file path, smoke-test results, and one human-review note.

Deployment path

Use GitHub Pages or another static hosting path if account setup is ready.

Fallback path

If deployment is blocked, submit the local HTML file and the completed deployment checklist.

Do not deploy

Anything with real names, emails, grades, health details, identity information, credentials, private prompts, or secret keys.
