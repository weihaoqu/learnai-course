29-34 min

Protect the last working version.

Fast AI-assisted building works only if students preserve stable states. Do not pile new features onto broken code.

1. Make one change

Ask the agent for one small completion or polish task, not a bundle of unrelated features.

2. Test immediately

Run the normal case, edge case, privacy check, and usability check before continuing.

3. Save a checkpoint

When it works, save or commit that state before starting the next change.

4. Stop if broken

If the app fails, debug that failure first. Record expected behavior, actual behavior, and any error text.

5. Roll back when needed

If the fix path gets messy, return to the last working version and try a smaller prompt.

6. Explain the diff

Before submitting, explain the change the agent made and why it improved the app.

Advanced case: SEO analyzer

A live SEO analyzer that fetches arbitrary websites is a backend or proxy project. For Week 10, transfer the PRD, plan review, test, and checkpoint workflow, not the backend architecture, unless the instructor explicitly approves that scope.

Advanced case: persistent rankings

If a database migration or deployment change breaks the app, roll back to the last working checkpoint and retry with a clearer prompt naming the current data source, target schema, data types, migrations, and verification checks. Persistent storage, Postgres, secrets, scraping, and migrations are outside the required static deployment path and require instructor approval.

Pre-deploy understanding check

Before deploying, ask what changed, which files ship, what was tested, where the rollback point is, and which code path you can explain. For advanced full-stack apps, also ask what data is stored, where secrets or environment variables live, what framework or database is used, and whether deployment reuses the same database or creates a new one. Required static projects should have no secrets in frontend code and should publish only HTML, CSS, JavaScript, and safe assets.

34-37 min

Generative AI apps improve through evidence loops.

A fast prototype is useful because it gives you something to test. It is not proof that the system is ready for real users.

Scope

Name the job, user, boundary, and success criteria.

Prototype

Build the smallest version that can be tested.

Internal test

Try normal cases, edge cases, privacy cases, and confusing inputs.

Improve

Fix the prompt, interface, rules, examples, or source pack.

Deploy

Share only after checks pass and the boundary is clear.

Monitor

Record failures as fix tickets or known limitations.

Static-course translation

For this class, monitoring means opening the shared link, testing it again, and recording what failed. It does not mean adding live analytics, user tracking, an LLM API, or a backend.

scope -> prototype -> internal test -> improve -> deploy -> monitor -> loop back

37-42 min

Static app architecture is small on purpose.

A complete static project can be a single HTML file, or a small folder of public files. Every file that ships can be read by the browser.

Single-file path

index.html contains HTML, CSS, and JavaScript. Best for simple student prototypes.

Folder path

index.html, styles.css, app.js, and public assets. Best when the app is getting larger.

What deploys

HTML, CSS, JS, images, and sample data that are safe to be public.

What does not deploy

Secrets, private prompts, account tokens, real student data, hidden answer keys, or files with personal details.

Ask students to point to where structure, style, behavior, and data live in their own project.

Final artifact

Week 10 Complete Project Packet

Submit the Reviewable Build Plan artifacts in order, then add the static link or fallback, smoke-test evidence, privacy/safety note, and human-review evidence.

Packet evaluation

Grade the plan, not prompt length.

The Reviewable Build Plan is worth 20-25% of the Week 10 Complete Project Packet evaluation. Strong work shows concrete decisions and a reviewable path before more edits.

Decision clarity

The user, purpose, boundary, and success checks are specific enough for a classmate to critique.

Spec focus

The spec describes one small behavior with inputs, outputs or states, and non-goals.

Ticket quality

The 3-5 tickets are small, local, and include blocker notes plus acceptance checks.

First Vertical Slice

The slice is a candidate end-to-end behavior to build or inspect, not unrelated feature expansion.

Review question

The question helps a reviewer catch risk, unclear scope, missing evidence, or blind AI acceptance before more edits.

Course boundary

Students are not required to independently use /implement or /code-review for this rubric.

Reward concrete decisions, small reviewable plans, and student pushback. Do not reward long prompts or passive acceptance of model output.
