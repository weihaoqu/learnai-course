Week 13: AI-Assisted Security Review for Final Web Apps
Slide 1
60-minute final-app review lab

Before showcase, inspect what could go wrong.

Week 13 is a practical review of the final static web app and the AI-agent workflow used to build it. Students leave with evidence of security review, not a vague promise that the app is safe.

In class

Scan the app, run adversarial tests, ask an agent for review help, and triage findings.

Outcome

A Week 13 Security Review Packet for the Week 14 presentation.

Boundary

Student review only. No real attacks, no credentials, no private data, no auto-push, and no professional security guarantee.

Pacing: 4 minutes. Keep this anchored to their own Week 10-11 project artifacts.
4-8 min

Use expert sources as a checklist, not as vocabulary homework.

For a one-hour class, we adapt only the risks students can see in their own projects.

Core sources

  • OWASP GenAI LLM Top 10: selected student-app risks.
  • GitHub Push Protection: secret leaks should be blocked before reaching repo history.
  • OpenAI Safety Best Practices: adversarial testing, human review, constrained inputs, and limitations.

Do not overclaim

  • This class is not professional penetration testing.
  • Optional advanced sources are instructor reference only.
  • An AI review is a second set of eyes, not a verdict.

8-12 min

The review path has six checkpoints.

A manageable review turns security from anxiety into a repeatable habit.

Map

Name assets, entry points, boundaries, and actions.

Scan

Check static files, inputs, outputs, links, data, and repo content.

Test

Run two adversarial tests safely.

Ask AI

Use an agent for review suggestions, not automatic fixes.

Triage

Fix, document limitation, or ask instructor.

Packet

Submit evidence before Week 14.

Review is evidence

The final presentation should say what was checked, what was fixed, and what limitation remains.

Reviewer needs new evidence

Review is strongest when the reviewer sees tests, screenshots, diffs, logs, source documents, or rendered output. Debate without new evidence is weaker.

12-18 min

Threat modeling starts with a small map.

For static apps, the important question is usually not "can hackers break the server?" It is "what is public, trusted, or action-taking?"

1

Assets

App files, sample data, project story, repo, deployed link, sources, prompts.

2

Entry points

Inputs, buttons, links, URL parameters, localStorage, pasted text, agent prompts.

3

Trust boundaries

Public browser, local files, GitHub, AI tool, user text, external sites.

4

Actions

Render output, save data, deploy, push, delete, install, share, claim.

Ask students to point to one asset and one entry point in their own app.
Optional case

Classify agent actions before allowing them.

Desktop and local-first agents are useful because they can act across files, apps, and connectors. That also means students need action-risk tiers before they trust an agent workflow.

Read-only

List files, inspect code, summarize a document, explain a screenshot.

Reversible write

Edit a local draft, create a copy, change a prototype file with diff review.

Irreversible write

Delete files, overwrite data, migrate repo history, rotate credentials.

External send

Push, deploy, email, post, invite, spend, or connect a real account.

Optional OpenWorker action-risk case
Use OpenWorker as a product-design and safety case only. Do not ask students to install it, connect accounts, or run desktop automations.
18-26 min

Use four risks students can inspect today.

These are simplified from expert AI security guidance and adapted to student static web apps.

Prompt injection

Untrusted text tries to redirect an AI agent or app behavior.

Sensitive disclosure

Secrets, tokens, personal data, private prompts, hidden answers, or repo files leak.

Improper output handling

User text or generated text is rendered, linked, or presented without validation or caveats.

Excessive agency

An agent can push, deploy, delete, install, spend, invite, or expose data without approval.

26-36 min

Run the static app security scan.

Click only the checks that are true for the current app. Unchecked items become review tasks.

36-41 min

Improper output handling is concrete.

Students do not need to become security engineers. They do need to know where output becomes public or trusted.

Inspect these patterns

  • Use of innerHTML with user-entered text.
  • Markdown or rich-text rendering from untrusted input.
  • URL parameters displayed on the page.
  • Generated text presented as fact without source or limitation.
  • Links created from user input.

Safer student move

  • Use plain text rendering for user input.
  • Validate or constrain inputs.
  • Label generated output as draft or suggestion.
  • Keep source-backed claims separate from generated text.
Review question for your app: Where does user input become visible output? Is it plain text, a link, HTML, saved state, or a claim?
Review add-on

Search is not verification.

AI search can save time, but the final answer may rely on snippets, summaries, retrieval results, stale pages, or weak sources.

  • Open the original page, not only the AI answer.
  • Check the date, source type, author, organization, and purpose.
  • Ask whether the page supports the exact sentence you want to say.
  • Use careful language: observed, sourced, uncertain, or prototype boundary.
  • Prefer official, primary, or expert sources for high-stakes claims.
Review question: Does every important claim in the app or Week 14 demo have an original source, direct test, or clear limitation?

Source concept: instructor-provided transcript on AI web search limits. Rewritten for final-project security and reliability review.

Use this to catch polished but unsupported claims. AI-assisted search is useful, but the student still owns source inspection before presenting.
41-46 min

Secrets should never enter public files or repo history.

GitHub push protection is a practical example: the best time to catch a secret is before it reaches the repository.

Never publish
API keys, service tokens, passwords, private prompts, hidden answer keys, student data, private repo content.
Never paste into AI
.env files, tokens, credentials, private student data, hidden answer keys, or sensitive internal files.
If found
Stop sharing, remove it, revoke or rotate the real secret, document the fix, and ask instructor before redeploying.
GitHub Push Protection
Use only fake secret examples. Do not display a real key format from a real account.
46-51 min

Ask the agent for review help, not authority.

The agent can generate a checklist and suspicious findings. The human still decides what is real, what to fix, and what to present.

Reinforce: do not paste secrets or sensitive data into the agent. Use file paths and descriptions when necessary.
51-56 min

Run safe adversarial tests against your own app.

These are simulated UI tests for student-owned projects. Do not test real services, classmates' accounts, or external systems.

56-58 min

Every finding needs a decision.

Do not let the security review become an endless cleanup session. Triage each issue before Week 14.

Fix before Week 14

Small, clear, testable issue that affects public sharing or user trust.

Document limitation

Real limitation that is acceptable for a static prototype if explained honestly.

Ask instructor

Secret, private data, high-stakes advice, unsafe tool action, or confusing risk.

Deployment is not the end

After sharing a link, record observed failures the same way you record internal test failures. Each one becomes a fix ticket, a known limitation for the presentation, or an instructor question.

Source concept: DeepLearning.AI, Generative AI for Everyone. Referenced for final-project security triage.

Minimum sufficient fix

Prefer the smallest change that removes or clearly bounds the risk. Do not let an AI agent turn a one-line validation fix into a new framework, backend, account system, or unrelated redesign.
