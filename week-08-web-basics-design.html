6-min design check

Before building, run a /grill-me requirements interview.

Matt Pocock's /grill-me skill turns a loose idea into decisions by asking one question at a time. Use it before the first build prompt, while the idea is still cheap to change.

Use it for

Target user, real problem, core interaction, constraints, examples, success test, and what should not be built yet.

Answer actively

The agent may suggest answers, but you own the decisions. Accept, revise, or reject any recommendation that misses your user or scope.

Stop condition

Move on when the agent can restate the user, problem, interaction, constraints, success test, and one risk.

Student rule

Use classroom-safe details. Do not paste private data, account information, or real sensitive user stories.

Optional protocol

Use a mini-grill, then write the prompt contract.

The interview is a bridge from idea to build instructions. It should end with decisions the student can paste into the Week 8 prompt contract.

1. Start fresh

Use a clean chat when possible so old context does not steer the interview.

2. Give the loose idea

Name the one-screen app idea, target class task, and what feels unclear.

3. Answer one at a time

Let the agent ask one question per turn. Revise weak recommendations instead of agreeing automatically.

4. Restate decisions

Ask for the final user, problem, interaction, constraints, success test, and risk before writing the build prompt.

Grill my one-screen app idea. Ask one question at a time. For each question, give your recommended answer. Stop when you can restate the user, problem, interaction, constraints, success test, and one risk.

Advanced sibling: /grill-with-docs can read a repo and capture resolved terms or decisions in docs. Treat it as instructor-guided because it is stateful and may write files.

If a question cannot be answered by conversation, stop the grill and build a disposable sketch or example. The technique supports prototyping; it does not replace prototyping, testing, or human design judgment.
Optional case study

Case study: plan an SEO analyzer before prompting.

Use this as PRD and wireframe practice, not as a required backend project. A live tool that fetches arbitrary websites needs proxy handling, scraping limits, and instructor approval.

PRD

What it should do

User enters a public website URL. The app reports metadata, search/social preview details, basic load signals, and improvement suggestions.

Wireframe

First screen

URL input, Analyze button, score or status summary, findings list, Google/social preview cards, and a visible error state.

Vocabulary

Words that steer the agent

Use domain terms such as SEO tags, meta tags, HTML head, title, description, social preview, responsive layout, and edge case.

Boundary

Static-course version

Students can plan the workflow or analyze sample HTML. They should not build a live URL fetcher unless the instructor explicitly changes the project scope.

48-53 min

Formative quiz: prompting apps.

Reveal each answer after students choose. The pattern is specificity first, then iteration after seeing the result.

1. "Make me a birthday card thing" produced a static image. What improves the prompt?
  • Ask the chatbot to try harder.
  • Give specifics about collected information and the output.
  • Keep the prompt vague.
  • Use more programming words.

Answer: Give specifics about the information to collect and what the output should look like.

2. A table tennis game works partly, but difficulty and styling are wrong. Best next step?
  • Conclude AI prompting cannot work for games.
  • Start over with an even longer prompt.
  • Ask it to debug itself without details.
  • Use follow-up prompts to add and fix features one at a time.

Answer: Send follow-up prompts that describe one concrete fix or feature at a time.

3. The basic table tennis game works. How should you add difficulty levels and styling?
  • Assume no more features can be added.
  • Only one-at-a-time prompts ever work.
  • Add features with follow-up prompts, or describe all wanted changes in one detailed prompt.
  • Only one long prompt works.

Answer: Either approach can work. What matters is clear detail and testing the result.

4. How important is the order of prompt building blocks?
  • Extremely critical.
  • Not very important; AI can understand different arrangements.
  • It must always follow a strict sequence.
  • It determines processing speed.

Answer: Not very important. Goal, inputs, output, layout, and features can be arranged in different orders.

5. A to-do app needs checkboxes so users can mark tasks complete. How do you add it?
  • Describe the new feature to the chatbot and ask it to add it to the existing app.
  • Build a completely new app from scratch.
  • Assume to-do apps cannot be modified.
  • Learn all JavaScript before asking for the change.

Answer: Describe the checkbox feature clearly, then test the updated app.

This is a formative LearnAI check, not a copied graded quiz. After the answers, ask one student to explain one generated code section in plain language before moving to peer critique.
